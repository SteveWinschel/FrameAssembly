## 2. Multi-Layer AI & Search Engine Architecture

1. **In-Context Agentic Discovery & Search Engine SEO (Primary Priority)**:
   - Because developers and AI agents rarely search for a custom DSL by name (`"FrameAssembly"` or `".fasm"`), every high-authority surface (`README.md`, `Cargo.toml`, `src/lib.rs`, `docs.rs` module pages, `docs/*.md`, and `llms.txt`) must be engineered around **problem-intent queries** and **ecosystem tool comparisons**.
2. **Pre-Training Corpus Survival (Dual-Homing Strategy)**:
   - Because `.txt` files over 512 lines are dropped by The Stack v2 and `.fasm` is not in upstream `go-enry` `languages.yml`, dual-home all grammar rules and examples across:
     1. **Chunked Markdown (`docs/*.md` and `README.md`, `< 50 KB` each)**
     2. **Rust Source Docstrings (`src/**/*.rs`, `< 50 KB` each, `>= 50` words, `15%–35%` comment ratio)**
     3. **Verified DSL Corpus (`examples/<layer>/<protocol>/<protocol>_<scenario>.fasm`, `2,611` scenarios)**
     4. **Formal Grammars (`grammar.ebnf`, `frameassembly.gbnf`, `frameassembly.lark`)**

## 4. 5-Way Constrained Decoding & IDE Grammar Lockstep Rules

FrameAssembly maintains a 5-way grammar and parser synchronization invariant across:
1. **`src/lexer/mod.rs` & `src/parser/`**: Ground-truth Rust tokenizer and protocol-scoped combinator parser.
2. **`grammar.ebnf` (ISO/IEC 14977 EBNF)**: Formal specification ingested by code LLM pre-training crawlers.
   - **Invariant**: Every non-terminal referenced on the RHS of a production must be defined on the LHS of a rule, and every terminal string must match `src/lexer/mod.rs`.
3. **`frameassembly.gbnf` (`llama.cpp` & MLC-AI `XGrammar` GBNF)**: Used for zero-overhead token-masking constrained decoding in `llama.cpp`, `vLLM`, `SGLang`, and `TensorRT-LLM`.
   - **Invariants**: Must begin with `root ::= ...`, contain **zero left-recursive rules**, define every referenced rule name, and match all parser sub-keywords (including `"REPORT"` in `snmp-proto-field` and complete `TYPE` / `CHUNK` alternatives).
4. **`frameassembly.lark` (`llguidance` & `Outlines` Lark CFG)**: Used by Microsoft `llguidance` (OpenAI Structured Outputs / Guidance) and `Outlines` (`CFG`).
   - **Invariants**: Uses `start:` and `%ignore` directives. Because Earley/LALR lexers tokenize literal string keywords as distinct terminal types with higher priority than `IDENT`, any rule that accepts arbitrary unquoted identifiers or strings (`str_or_ident`) **must** explicitly union `IDENT | STRING` with contextual uppercase keyword tokens (e.g., `CNAME`, `TEXT`, `INIT`, `DATA`, `ACK`, `SYNC`, `REPORT`, etc.) so valid `.fasm` constructs like `ENCODING CNAME` or `CHUNK INIT` are never rejected by the lexer.
5. **`frameassembly-vscode/syntaxes/frameassembly.tmLanguage.json` (VS Code TextMate Grammar)**: Highlights all 81 protocol keywords, L2–L4 modifiers, `WAIT <int><ns|us|ms|s|m>`, and `HOST`/`FLOW`/`COMPILE`/`LOOP` blocks.

### Specific Grammar Audit Bugs to Prevent & Fix in QA
When auditing or updating the grammar files, explicitly check for and remediate these four historical drift patterns:
1. **Undefined Non-Terminal in `grammar.ebnf`**: `grammar.ebnf:607` referenced `string_char` without defining `string_char = ? any printable ASCII character except '"' or '\' ? | '\"' | '\\' ;`. Every non-terminal in `grammar.ebnf` must be defined.
2. **Overly Restricted `TYPE` and `CHUNK` Rules**: In `grammar.ebnf`, `frameassembly.gbnf`, and `frameassembly.lark`, generic `TYPE` and `CHUNK` productions must accept the full range of values accepted by `src/parser/` (`unsigned_int`, `str_or_ident`, and protocol-specific chunk/type tokens) rather than a truncated subset.
3. **Missing `"REPORT"` in SNMP Protocol Field**: Both `frameassembly.gbnf` (`snmp-proto-field`) and `frameassembly.lark` (`snmp_proto_field`) must include `"REPORT"` alongside `"GET"`, `"GETNEXT"`, `"RESPONSE"`, `"SET"`, `"TRAP"`, `"GETBULK"`, and `"INFORM"`.
4. **Lark Contextual Keyword Collision in `str_or_ident`**: In `frameassembly.lark`, include contextual uppercase keywords in `str_or_ident` so `llguidance` / `Outlines` Earley/LALR lexing never rejects unquoted uppercase tokens used as field values (such as `ENCODING CNAME` or `CHUNK INIT`).

## 5. Multi-Task SFT, FIM, DPO & 2025–2026 RLVR Compiler-Reward Architecture

### 5.1 Five-Task Synthetic Dataset Export (`2,611` `.fasm` Scenarios $\rightarrow$ `13,055` Instances)
From the verified `examples/**/*.fasm` corpus (`2,611` scenarios: `31` per protocol across 81 protocols + `100` multi-protocol topologies), deterministic dataset exporters synthesize **13,055 high-signal training instances** across 5 tasks (packaged with an **MLCommons Croissant 1.0 `croissant.json`** manifest and HuggingFace Dataset Card):
1. **Task 1 — Forward SFT: Natural-Language Prompt $\rightarrow$ `.fasm` Synthesis (`2,611` pairs)**: Maps `// PROMPT:` to the complete `.fasm` specification with chain-of-thought reasoning derived from `// TOKENS:` and block-level `// INSTRUCTION:` annotations.
2. **Task 2 — Repo-Level & File-Level Fill-in-the-Middle (`2,611` FIM triplets)**: Uses `<|repo_name|>`, `<|file_sep|>`, `<|fim_prefix|>`, `<|fim_suffix|>`, and `<|fim_middle|>` tokens to train code completion models to synthesize `FLOW` bodies from `HOST` declarations and `COMPILE` invocations.
3. **Task 3 — Inverse Wire-to-DSL Walkthrough (`2,611` pairs)**: Pairs deterministic PCAPNG packet dissections (frame count, nanosecond timestamps, Ethernet/IP/L4/L7 header fields, and byte lengths emitted by `backend::compile_program`) with the target `.fasm` program that synthesizes them.
4. **Task 4 — Contrastive DPO Preference Triplets (`2,611` triplets)**: Deterministically mutates valid `.fasm` ASTs with common LLM hallucinations (e.g., `+5ms` prefix delays, standalone `WAIT` lines, `HOST x = { IP: ... }`, `SPORT`/`DPORT`, mixed IPv4/IPv6 endpoints) to form `(prompt, chosen_valid_fasm, rejected_invalid_fasm)` preference pairs.
5. **Task 5 — Execution-Feedback Self-Repair & RLVR Trajectories (`2,611` trajectories)**: Pairs each mutated program and its exact `miette` compiler diagnostic span with the repaired `.fasm` solution for multi-turn compiler-in-the-loop self-repair.

### 5.2 4-Stage Hierarchical RLVR Reward Function ($R(x, y) \in [0.0, 1.0]$)
For 2025–2026 Reinforcement Learning with Verifiable Rewards (**RLVR** / **DeepSeek-R1 GRPO**) training loops, FrameAssembly provides a fast (`< 1 ms` per rollout), deterministic, 4-stage hierarchical reward function $R(x, y) \in [0.0, 1.0]$:
- **Stage 1 — Lexical Validity ($R = 0.1$)**: `frameassembly::lexer::Token::lexer(y)` tokenizes the candidate `.fasm` program with zero `Err(())` lexer spans and zero forbidden hallucinated keywords.
- **Stage 2 — Syntactic AST Validity ($R = 0.3$)**: `frameassembly::parser::parse_program(y)` succeeds, producing a complete `Program` AST containing `HOST`, parameterized `FLOW`, and `COMPILE` blocks.
- **Stage 3 — Semantic & Dual-Stack Type Validity ($R = 0.6$)**: `frameassembly::parser::validate_semantics(&program, y)` succeeds, confirming all referenced hosts and flows exist, argument counts match flow parameter arities, and every statement satisfies IPv4/IPv6 endpoint homogeneity.
- **Stage 4 — Wire Compilation & RFC Dissection Verification ($R = 1.0$)**: `frameassembly::backend::compile_program(&program)` emits deterministic wire frames with valid RFC checksums (IPv4 header, TCP/UDP/ICMPv6 pseudo-header, SCTP CRC-32c, DNP3 CRC-16) and satisfies all protocol/field constraints specified in prompt $x$.
